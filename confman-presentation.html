The Problem

Why Build Confman?

Configuration lived in a 15 GB git repository of JSON files. No governance, no audit trail, no access control, no consistency guarantees.

Functional Requirements

  • ▸ Hierarchical key-value store with namespaces
  • ▸ RBAC: viewer, editor, publisher, admin
  • ▸ Four-eyes publishing workflow
  • ▸ Schema validation (JSON Schema)
  • ▸ Immutable version history + audit trail
  • ▸ REST API with content negotiation

Non-Functional Requirements

  • ▸ 100K+ keys, 100–200 req/sec
  • ▸ 70–90% reads, burst write patterns
  • ▸ Strong consistency for writes, bounded staleness for reads
  • ▸ Survive single-node failure (fault tolerant)
  • ▸ VMs / bare metal — no Kubernetes
  • ▸ Azure AD / OIDC for authentication

January 24–30

The Distributed Systems Reckoning

Three fundamental bugs — each a classic Raft misunderstanding:

  • Audit Duplication — N events per command (one per node). Misunderstanding of state machine Apply() semantics.
    FIX: Apply creates event on ALL nodes identically
  • Audit Not Replicated (GitHub #2) — Events only created on the leader node. All durable state must flow through the consensus log.
    FIX: Deterministic IDs + idempotent upsert
  • Snapshots Empty (GitHub #3) — Snapshot serialization didn't include actual data. Snapshot = complete state.
    FIX: Full-state JSON snapshot serialization

Lesson: Distributed systems correctness requires explicit thinking about which node does what work.

February 1–2

Making It Correct

From "does data arrive?" to "is it consistent?"

  • ◆
    Linearizable Reads

    ReadBarrierMiddleware calls ApplyReadBarrierAsync() on every GET — ensures reads reflect latest committed writes.

  • ◆
    Leader Forwarding

    Writes return HTTP 307 redirect to current leader. Clients must follow redirects.

  • ◆
    Silent RBAC Bug

    Role "reader" ≠ policy "read" — entire auth system was broken. Fixed by aligning to viewer | editor | publisher | admin.

  • ◆
    Strongly-Typed Audit Actions

    Replaced string literals with AuditAction value object for compile-time safety.

February 5–10

The Performance Sprint

Three tiers of optimization → 3.6x write throughput

Tier 1 — Config Wins (~2x)

  • LiteDB Connection=direct
  • WAL FlushInterval=100ms
  • HTTP/2 for Raft RPCs
  • Remove pre-write existence check

Tier 2 — Eliminate Waste

  • Remove post-write poll loop
  • SerializeToUtf8Bytes
  • Eliminate read-before-write
  • Leader lease via TryGetLeaseToken

Tier 3 — Write Batching (3.6x)

  • Channel<T> + flush loop
  • BatchCommand groups concurrent writes
  • Amortize Raft quorum cost
  • MessagePack + LZ4 serialization
Before: 124 req/s → After: 453 req/s

Key Takeaways

  1. Design first, code second — Four brainstorm documents before any implementation. The architecture held up throughout.
  2. Distributed systems bugs are subtle — Each bug was a classic Raft misunderstanding that only appeared in a real cluster.
  3. Measure before you optimize — Benchmarks immediately surfaced a lurking WAL bug and identified the real bottlenecks.
  4. Performance optimization is layered — Config wins → waste elimination → architectural change. Each layer sets up the next.
  5. Memory is harder than throughput — The PrivateMemory mode gave 30-50% throughput but caused 40x memory bloat.
  6. Know when to change the architecture — When snapshots hit the ceiling, redesign the data path rather than tune harder.
  7. Document the invariants — snapshot_time < election_timeout < request_timeout
